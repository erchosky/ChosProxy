# ADR-0026: ChosOAST (out-of-band interaction testing)

* Status: Accepted
* Date: 2026-11-11

## Context
Milestone 18 adds the Collaborator-equivalent of spec addendum §68. ChosProxy
must generate unique identifiers tied to the project and to the requests
that carried them, record DNS, HTTP and HTTPS interactions with timestamp,
protocol, origin and raw data, and show the chain Finding → request →
identifier → interaction → evidence. It must work without any
ChosProxy-operated cloud: local and self-hosted modes, self-hosted
preferred.

## Decisions
1. **Identifiers carry a checksum.** 16 random base32 characters (80 bits)
   plus 4 characters of a SHA-256 checksum. Any server can recognise them
   in a DNS name, Host header, path or body without knowing which
   identifiers exist, and ordinary text practically never matches. The
   alphabet is DNS-safe and case-insensitive (resolvers may randomise case).
2. **One small crate, `chosproxy-oast`, is the server and the client.** The
   same interaction server runs inside ChosProxy (Local mode) and as the
   `chosoast` binary on a machine the tester controls (Self-hosted mode).
3. **The server only observes.** HTTP and HTTPS clients get a fixed
   response; nothing received is executed, stored on the server's disk or
   reflected. The DNS part is authoritative for one zone only: `A`/`AAAA`
   answers with TTL 0 inside the zone, REFUSED outside it, no recursion,
   no compression pointers read, and a per-source budget of 20 queries per
   second (over-budget queries are neither answered nor recorded). Answers
   are at most 32 bytes larger than the question, so the server is useless
   as an amplifier. No DNS library was available offline; the parser is
   ~200 lines and part of the robustness harness.
4. **Self-hosted polling is authenticated and pinned.** `chosoast` creates
   a 256-bit token and a self-signed certificate on first start (both
   `0600` in a `0700` folder) and prints the token once and the
   certificate's SHA-256. ChosProxy polls `GET
   /chosoast/v1/interactions?after=<seq>` over TLS, accepting only that
   certificate; the token is compared in constant time. No public CA or
   domain certificate is needed, and nothing in between can read the token
   or the interactions. The server keeps interactions in memory only.
5. **Only this project's interactions are stored.** Payloads are rows in
   the project (schema v14). An interaction is stored only if its
   identifier belongs to one of them, keyed by server and sequence so a
   repeated poll stores nothing twice; others are counted as ignored. A
   self-hosted server shared by several projects therefore never mixes
   their data.
6. **Links are found in traffic, not declared.** A linker scans every new
   stored request (any tool) for this project's identifiers. Wherever the
   tester puts a payload — Repeater, Fuzzer, the lab browser — the request
   that carried it is known. Requests sent to the OAST server itself (its
   zone, or the local server's host and port) are not links, so opening a
   payload URL yourself proves nothing and creates nothing.
7. **Findings need both halves.** An identifier with a carrying request and
   an interaction becomes an automatic finding (source `oast`), one per DNS
   and HTTP family: "External service interaction", Medium, Firm, the
   carrying request as evidence and the interaction in the description.
   Findings are merged and reopened like passive ones.
8. **Off by default.** Nothing listens and nothing is polled until the
   tester picks a mode. The local server binds `127.0.0.1` unless a network
   address is chosen, which is warned about in the UI and the event log.

## Consequences
* Local mode covers labs on this machine or a lab network; DNS payloads
  there need the lab's resolver to forward the zone. Self-hosted mode
  covers real targets once a zone is delegated to the server.
* HTTPS interactions on a self-hosted server use its self-signed
  certificate: clients that verify certificates fail the handshake, and
  only those that do not are recorded as HTTPS. DNS and HTTP are the
  reliable channels. An ACME certificate is future work.
* "External OAST provider" plugins (spec §68) need plugins that may send
  traffic (`network.send`), which API v1 reserves; they move to M23.
* SMTP and other protocols are not implemented; the interaction model
  (`protocol` + raw bytes) has room for them.
* ChosOAST ships no injection payload lists: it provides identifiers and
  records callbacks, and the tester decides where identifiers go.
